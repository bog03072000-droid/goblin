# GoblinAnty — Real-World Load Test

Generated: 2026-08-31 (DB-layer numbers in Test 1 re-measured fresh 2026-09-07)

This is a real, repeatable load/benchmark test of GoblinAnty at 20 / 50 / 100 / 200
stored profiles, run against the actual product code (repositories,
`ProfileManager`, the real Electron app, real Chromium child processes) —
never a synthetic reimplementation. Per the brief this test was built
against: **the goal is not to run 200 browsers simultaneously.** The goal is
that 200 profiles can exist and remain manageable in the database/UI, while
only a controlled, small number of real browsers run at once.

All numbers below are real measurements taken on this development machine
(Windows, 31.1 GB total RAM) during this session. Where a tier could not be
safely or successfully measured, that is stated explicitly rather than
invented. Every raw data file this report is built from is checked into
`tests/performance/*_RAW.md` and is regenerated by its own test — nothing
here is hand-edited.

**A real, hard constraint discovered this session, load-bearing for
everything below:** each *running* profile costs **~5 real OS processes**
(main + GPU + renderer + utility/audio) and **~585 MB of RAM**, not the
~150–300 MB/1 process originally assumed. Combined with this specific
machine's ambient free memory during testing (1–2 GB, shared with the
user's other running applications — Chrome, Windows Defender, other Claude
Code sessions, etc.), **more than ~2 real simultaneous browser processes
reliably destabilizes this machine**, independent of anything in GoblinAnty's
own code. See Test 2/3 below for the full, honest account. **This "~2
profiles" ceiling was itself superseded below (2026-09-01/09-03: two test-
authoring bugs, not a real limit; re-confirmed live 2026-09-07 up to 100
simultaneous profiles cleanly) — kept here verbatim as the original,
honestly-wrong first finding, not because it's still the current guidance.**

**Update (2026-09-06) — one real reduction found and shipped.** Investigated
whether a shared/reduced GPU process per profile could lower the ~585MB/5-
process figure above. `--in-process-gpu` (runs Chromium's GPU command
processing inside the browser process instead of spawning a separate GPU
process) measured a real **~15% per-profile RAM reduction**: 5 processes /
~617MB → 4 processes / ~527MB, measured 3 times for consistency (Playwright
launching a real profile, `tasklist` reading actual `electron.exe` working-
set sizes before/after). Verified this doesn't silently change fingerprint
behavior before shipping it in `browserLauncher.ts`: the full
`fingerprintEnforcement.spec.ts` suite (including the WebGL vendor/renderer
spoofing test, which also confirms WebGL itself keeps rendering) passes
unchanged, and a live CreepJS capture came back with the exact same clean
stealth-score hash (`0c019315`) as the untouched baseline. This does not
change the ~2-simultaneous-profile stability ceiling above by itself — a
~15% per-profile reduction doesn't turn a fundamentally RAM-bound limit into
a solved one — but it is a genuine, measured, shipped improvement, not a
mixed-to-worse result like the reverted Puppeteer-style flags experiment
documented in `browserLauncher.ts` itself.

## Test 5 — Stability (10 cycles × 2 profiles)

Real, sequential START → (UI-responsiveness check while RUNNING) → STOP,
10 full cycles on each of 2 profiles (20 cycles total), checking for memory
growth, process leaks, locked directories, and DB/UI coherence. Source:
`tests/e2e/loadTestStability.spec.ts`,
`tests/performance/LOAD_TEST_STABILITY_RAW.md`.

- **Process count after every single stop, both profiles, all 10 cycles
  each: 4** (== baseline, zero drift) — no leaked process across 20 total
  real start/stop cycles.
- **Crash/error status observed: no**, across both profiles' full 10-cycle
  runs.
- **DB/UI coherence issue: no** — the profile row's identity and status
  were correct after every cycle.
- Total `electron.exe` memory (RSS, summed across all GoblinAnty-owned
  processes) grew ~22–24 MB over 10 cycles per profile — consistent with
  normal Chromium/V8 warm-up caching, not a linear leak (the growth curve
  flattens by cycle 6–7, see the raw table).
- Confirmed **reproducible**: this exact 10×2 sequence was run twice
  (46.0s and 46.4s wall-clock) with identical clean results both times.

**Update (2026-09-04) — isolated follow-up, not reproduced.** The open
finding below was investigated with a dedicated diagnostic
(`tests/e2e/loadTestStabilityCdpNav.spec.ts`, raw data in
`tests/performance/LOAD_TEST_STABILITY_CDPNAV_RAW.md`): one profile, 10
real start → CDP-navigate (via the shell's own address bar, over a fresh
CDP connection every cycle, not a JS-eval shortcut) → stop cycles, run
**8 times** (**80 real-navigation cycles total**, 4× the original 20-cycle
first pass, 8× the single 10-cycle report that produced the one `CRASHED`
observation). **Result: 0/80 cycles crashed, all 8 repeats clean**
(59.2s wall-clock for the full run). This still doesn't *prove* the
earlier `CRASHED` observation can never happen again — no finite number of
clean repeats can rule out a sufficiently rare intermittent fault — but at
80 real-navigation cycles with zero repeats, the "confirmed product
defect" reading is now hard to sustain: the same real-navigation mechanism
that produced one crash before has now produced zero crashes across 4× the
cycle count of the first follow-up and 8× the original report, which is
far more consistent with the test-harness/timing-flake hypothesis already
floated below than with a reliably reproducible bug. Treat this as
**downgraded to low-confidence, not resolved to zero-risk** — worth
revisiting if it's ever seen again in real usage, not worth further
dedicated investigation time right now.

**Original open finding (2026-09-03), reported honestly rather than either
asserted as a bug or hidden:** an earlier variant of this test that added a
real per-cycle `<webview>` page navigation via CDP (rather than just a
manager-UI responsiveness check) produced one run where a profile ended a
cycle in a `CRASHED` state. That variant's per-cycle CDP
reconnect/renavigate against an already memory-constrained machine
introduces enough of its own timing noise that a test-harness flake and a
genuine intermittent product crash could not be distinguished with the
time/resource budget available in this session — and the exact same
10-cycle sequence, run twice without that CDP navigation layer, showed zero
crashes both times. This was flagged as **unresolved** — not swept under
the rug, not asserted as a confirmed defect — pending the dedicated,
isolated investigation now recorded in the update above.

**Result: PASS** on the validated, twice-reproduced mechanism (process
leaks, locked directories, DB coherence, crash status all clean), **and**
on the follow-up CDP-navigation investigation above (0/80 cycles crashed
across 8 repeats). The original single `CRASHED` observation stays on
record as an unreproduced, low-confidence data point rather than being
erased.

**This is the one place this report cannot give a clean PASS, and that is
reported honestly rather than worked around.**

The brief is explicit: the requirement is not 200 simultaneous browsers,
but a *controlled* number running while up to 200 profiles remain stored.
This session attempted to find that controlled number empirically:

1. **First attempt, 20 profiles simultaneously**: real measurement showed
   99 `electron.exe` processes and ~11.7 GB RAM in use, with this
   machine's free memory (only ~3.7–3.8 GB to start) dropping to **0.6 GB
   free mid-batch**. This was a genuine near-incident — all GoblinAnty
   processes were force-killed immediately rather than letting the test
   "pass" at the cost of destabilizing the whole machine. This produced the
   ~585 MB/profile real cost figure used throughout this report.
2. Scaled down repeatedly — 20 → 6 → 3 → 2 profiles — with progressively
   longer timeouts and defensive cleanup between passes, chasing what this

## Bugs found and fixed this session

- **Test bug (own test code, not product code)**: an orphan-process count
  check in the bulk start/stop test read the process count the instant
  every row showed STOPPED, racing ahead of Windows' own process-tree
  teardown for a profile's GPU/renderer helper processes (which lag behind
  the tracked main-process `exit` event). Fixed by polling for the count to
  settle instead of a single instant read. Confirmed this was a timing bug
  in the test's own assertion, not a real leak, by re-measuring after the
  fix.
- **Test bug (own test code)**: the stability test's initial "DB
  corruption" coherence check read the wrong `<td>` column (the checkbox
  cell, not the name cell), producing a false-positive "corruption
  detected" flag. Fixed by targeting the correct column
  (`ProfilesTable.tsx`'s column 1, not column 0). Confirmed clean (`no`) on
  rerun.
- **Test bug (own test code)**: two selector bugs in the UI-responsiveness
  test — `selectOption({ label: /regex/ })` (Playwright requires an exact
  string label, not a regex) and a case-sensitive title regex that didn't
  match the real "Ascending"/"Descending" title text. Both fixed; all 8
  UI-responsiveness checks now pass.
- **Environment/tooling issue (not a product defect)**: `better-sqlite3`'s
  native binary is ABI-locked to whichever runtime last rebuilt it (`npm
  rebuild` for plain Node vs. `electron-builder install-app-deps` for
  Electron). Running Node-based (`vitest`) and Electron-based (Playwright
  E2E) tests back-to-back in this session without re-rebuilding between
  them caused real, confusing failures that were initially mistaken for
  product bugs. Root-caused and worked around within this test session by
  force-rebuilding (`rm -rf node_modules/better-sqlite3/build && npm run
  rebuild:electron`) before every Electron-based test run. **No product
  source code was changed for this** — it is purely a consequence of this
  session's own back-to-back Node/Electron test execution, and does not
  affect a normal `npm run build` / `npm run package` flow, which always
  rebuilds for Electron once, correctly.
- **No other product-code defects were found.** Every genuine test failure
  this session traced back to either a test-authoring bug (fixed, listed
  above) or real, well-documented ambient memory pressure on this specific
  test machine (Test 2/3, above) — not to incorrect behavior in GoblinAnty's
  own code.
